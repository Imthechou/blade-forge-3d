## 二、S1 的最终做法

### 问题

P3 交付后 S1 的对比σ 是 0.2041，而改动前是 0.2666。但那个 0.2666 来自
「矿石被当成抛光合金」（`metalness 0.92`）这个**错误状态** —— 拿它当目标本身就不对。

### 试过并否掉的

| 方案 | 结果 | 否掉原因 |
|---|---|---|
| 金属度下界 0.55 | σ 0.2043，hf −15% | 矿石变塑料：镜面退场后无漫反射结构 |
| `floor()` 大块面 + 中频颗粒 | 数字涨了，**图为马赛克拼贴** | 硬量化，且频率算错（见 4.1） |
| 提高 relief 到 0.45 | σ 反而 −0.0072 | 不但没用，还引入编织纹 |

### 最终采用的（零额外成本）

```glsl
float facetN = k3dPat[0];                          // 已算好，免费
float midN   = k3dNoise2( vBladeLocal.xy * 30.0 );  // 4 次 hash
float ridgeN = 1.0 - abs( midN * 2.0 - 1.0 );       // 复用，0 成本
```

关键洞察：`k3dPat[0]` 在 `mapFragment` 里**早就算好了**（无论用不用都要付这笔采样钱），
拿它当大块断面是**完全免费**的。S1 的噪声预算从 24 次 hash 降到 4 次。

### 结果

| 指标 | P3 | 现在 | 变化 |
|---|---|---|---|
| 对比σ | 0.2041 | **0.2348** | **+15.0%** |
| hlEnergy | 0.000714 | **0.003779** | **+429%** |
| hfEnergy | 0.070055 | **0.145064** | **+107%** |
| 视觉 | 马赛克/编织纹 | 晶面高光 + 明暗断面 | 见 `shots/p3look/S1.jpg` |

## 四、我错了 6 次（这轮最重要的一节）

### 4.1 频率没换算成实际尺度（第 1 次）

```glsl
floor( x * 26.0 )   // 注释写"约 26 格"
```

`vBladeLocal.x` 只有 0~0.35，`26 × 0.35 = 9.1` —— **真实只有 9 格**。
所谓"中频颗粒"实际是 9×11 的大方块，所以看起来像拼贴瓷砖。
同理 `floor(x*3.4)` 在整个模型上只取 2 个值。

### 4.2 用错了指标（第 2 次）

`hfEnergy`（拉普拉斯高频能量）**无法区分"真实结构"与"程序化网格缺陷"**。

最典型的反证：S3 的 `relief=0` 时 σ=0.1547、hf=0.0715，数字最差，
但那张图是全程最干净的。而 `relief=0.26` 时 hf=0.1655 看着更好，
其中却混着网格纹的贡献。

**教训：pixel 统计只能回答"有没有变化"，不能回答"好不好"。**

### 4.3 分析层漏算（第 3 次）

我花了很久分析"改 albedo 为什么没用"，最后才发现：

```
S1 生效金属度 = 0.92 × mix(0.72, 1.0, 0) = 0.66
→ 漫反射只占 (1−0.66) = 34%，其余 66% 是环境镜面反射
```

所以改 albedo（颜色层）最多只动到 34% 的那一半，σ 的主载是镜面通道。
这个数在动手前就该算出来。

### 4.4 截图装置是 DPR=1（第 4 次）

`_p3look.mjs` 最初写死 `deviceScaleFactor: 1`，理由是"看结构不用高分辨率"——
**这个理由错的**。矿石只占视口 47%×37%，DPR=1 下只有约 180×140 px，
而我输出宽固定 360px → **2× 上采样**。我看到的"方块"有相当部分是自己的采样阶梯。

### 4.5 裁剪强制正方形（第 5 次，代价最大）

`_p3look.mjs` 把裁剪框拉成正方形（`side = max(w,h)`）。

S3 刀胚 `fillW` 只有 17.3%，模型在画布上原生只有 **101×404 像素**。
压成正方形后刀身只剩约 85px 宽 → 细密纹理 undersample → **摩尔纹**。

判决实验 `_p3alias.mjs`（同一帧、只改输出方式）：

| 输出方式 | hf |
|---|---|
| A 强制正方形 340 | 0.12783 |
| B 自然比例 340 | 0.032224（−75%）|
| C 自然比例 900 | 0.007027（−94%）|

**我据此在 S3 上「修」了三轮参数**（fbm 化锤痕、`aniso` 0.72→0.32、`relief` 0.26→0.10），
全是修自己的采样假象。修好采样后重扫，0.26 本来就是对的 —— 已全部回退。

### 4.6 用被抢占的机器测性能（第 6 次）

`bench-browser.mjs` 连续跑出 warm p50 = 23.0 / 57.1 / 68.3 / 65.3，
`max` 在 146 / 310 / 669ms 之间跳。我一度以为是自己的改动引入回退，
做了两轮"优化"（缓存复用、降噪声阶数）。

真相：

```
CPU 当前总负载: 72%
r5apex_dx12   CPU 10656s   内存 3026 MB   ← Apex Legends 在跑
```

**性能数字不可信。** 我没有去结束用户正在运行的游戏进程；
两轮优化本身是有效的（S1 噪声从 24 次 hash → 4 次），但效果无法在当前环境量化。

## 五、核心教训（写给下一次的自己）

1. **先证明测量装置是对的，再相信测量结果。**
   这轮有三个独立缺陷（DPR、正方形裁剪、陈旧帧），每一个都会让结论反向。

2. **改参数前先做单变量扫描。**
   `_p3relief.mjs` 一次就定位了 S1 编织纹的阈值；而在那之前我凭猜改了三轮代码。

3. **阶梯式排除，每步都要有判决性证据。**
   "关掉 X 看缺陷是否消失"比"分析 X 为什么可能导致缺陷"快 10 倍。

4. **细长物体不能用方形裁剪。** 评测装置的分辨率必须高于被评对象的像素尺度。

5. **指标只能证伪，不能证好。** 视觉最终必须看图，但看图必须先保证采样正确。

6. **环境本身是变量。** 跑性能前先 `Get-Process` 看一眼有没有游戏/编译在抢 CPU。

## 六、未达成（如实记录）

1. **性能未能在干净环境验证。** 本机 CPU 负载 72%（Apex 在跑）。
   两轮优化的代码改进是确定性的（hash 次数 24 → 4），但**效果无法量化**。
   需要在干净机器上重跑 `bench-browser.mjs`。

2. **S2 底部有弧形条纹**（见 `shots/p3look/S2.jpg`）。
   这是钢液流动项（`sin` 三层波）的表现，属预期行为，但规律性偏强，
   不排除仍有微脊成分。未做隔离，未解决。

3. **S1 的 σ 是 0.2348，仍低于原始错误的 0.2666。**
   那个 0.2666 来自"矿石被当抛光合金"，不应作为目标；
   但"矿石该有多大的明暗对比"这件事**没有任何权威依据**，只凭观感。

4. **仍无人眼多场景验证。** 本轮只看了 3 张 360px 小图（S1/S2/S3）。
   未覆盖：不同刀型、不同卡、变焦、旋转、真机。

5. **`_p3facet.mjs` 已废弃**（`finally` 里对空数组 `reduce` 会抛错掩盖真实异常），
   保留仅为留档，不要再用。
